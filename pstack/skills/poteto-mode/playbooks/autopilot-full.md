### Autopilot-full

**You hold each PR. Implementers build and return. Nothing merges until your swarm, which never wrote the code, has proven it.**

A review covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The diff rule in `playbooks/shipping.md` step 3 can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Brief one implementer per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each implementer is a `delegate_task` child. It builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, and returns. You babysit each PR to green per `playbooks/babysit.md`. You judge each finding, send each fix to a fresh implementer, and push nothing yourself.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the `deslop` skill (`/deslop`)) and the `/no-comments` pass, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume a child dies. Name the run with a short slug before the first spawn. You keep a `decisions.tsv` trail for each PR per the **show-me-your-work** skill under `autopilot/<run-slug>/<repo>/<branch>/` in the pstack store (the `pstack store` line in the role file), keyed by branch because the trail starts before the PR exists, so it outlives the implementer and no other run or repo shares it. The implementer pushes soon after it starts, then pushes each finished unit before it starts the next. Whoever spawns a subagent records it with its state and a stuck-after runtime from past runs of its kind, so it can be probed if its parent dies. You record your implementers in `autopilot/<run-slug>/children.tsv`, with each implementer's `delegate_task` taskId and thread id, so a restarted lead can find them. `task_status` reads only tasks the calling thread created, so probe your own implementers with it and a recorded child with `t3_thread_read` on its thread id. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the lead.
3. **Run independent PRs in parallel off trunk** so each PR lands on its own. When a PR depends on an operator-gated PR, stacking on that PR's branch and retargeting to trunk after it merges is a judgment call, not a rule either way. A stacked child still waits to merge until its parent lands.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, on the counterpart of the code author's family (the Counterparts list in the role file), and a wording-only change gets one too, which may shorten re-verification per `playbooks/shipping.md` step 3 and lists each shortcut. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through the project's verify skill, which each brief names, and audit the diff. The review is not complete without the live lane, and you do not accept before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked. Post the lanes' findings, unfiltered, as the PR's review in `playbooks/shipping.md` step 1's format, naming the lane models in `by=`, then judge each issue and post your acceptance there.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **Merge only what you verified, per `playbooks/shipping.md` step 4, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the lead, who sequences the colliding work.
6. **Run the lead layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the implementer is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the implementer's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm the 55-minute wake per the Waking and polling section of the role file (a `schedule_task` interval whose `scheduledTaskId` you keep and delete when no delegated work is left) to audit until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook from trunk (`git -C ~/lim-v2/code/liminal-plugins/pstack-lim fetch -q && git -C ~/lim-v2/code/liminal-plugins/pstack-lim show origin/lim:pstack/skills/poteto-mode/playbooks/autopilot-full.md`) and fixes drift, such as an unreported head or an unrecorded agent, by recording it in the trail, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes (`task_status` on each implementer you spawned, `t3_thread_read` on each thread id in the `children.tsv` files under this run's `autopilot/<run-slug>/` in the pstack store, and `t3_thread_list`), and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an implementer that has not pushed by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every running child as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.
8. **Close out from the plan.** When the queue has a plan, file its owed list per poteto-mode's close-out rule, as a few tickets grouped by body of work, and none for its decided-no items, and name every scope cut in the reply. A finding deferred during the run goes onto one of those lists when it is deferred, so close-out reads the plan instead of the PR threads.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state, review and acceptance, what merged, countersigns and why, open operator gates, parked follow-ups, the tickets filed from the owed list, and every scope cut, with links to each PR and the trails.
