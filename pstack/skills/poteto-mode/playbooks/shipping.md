### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then have each PR reviewed independently and accept it yourself before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, a `delegate_task` child on the counterpart of the code author's family (the Counterparts list in the role file, `~/lim-v2/AGENTS.md` or `~/lim-v2/CLAUDE.md`) and never the author, in its own worktree per poteto-mode's Subagents section, runs the change the way a user would through the project's verify skill, which its brief names, parent against head, and posts its review on that PR as one comment. The brief also names the repo's merge brief, `.agents/merge-brief.md`, because the review must cover what it requires. When the PR has a plan (`playbooks/multi-phase-plan.md`), the brief names the plan file and the PR's section. When the PR changes something a user can see or use, the verifier also makes the before-and-after screenshots or video that `playbooks/opening-a-pr.md` asks for, while it drives the change, and links them in its review. The brief points the verifier to this step, `~/.agents/skills/poteto-mode/playbooks/shipping.md` step 1, for the review's format, and does not copy it.

   The review reports what the verifier found. It carries no pass or fail word, and the verifier does not approve or reject. Its first line is `pstack-review: head=<head sha> base=<merge-base sha> by=<model>`. Under it comes one line for each required box of the PR's plan section, by the id `check-plan.mjs` prints: `box <id>: done`, `box <id>: done. <note>`, `box <id>: failed. issue <n>`, `box <id>: n/a. <reason>`, or `box <id>: skipped. <what did not run>`. An id is lowercase letters with at most one numeric suffix, so `item-2` reads and `item-2-r2` does not. A note follows the status after a period and a space, never in brackets, and a period with nothing after it does not read. `done` means the box ran and met its requirement. A box that ran and did not meet it is `failed` and names its issue, and it stays `failed` even when you accept the failure. A box carried by step 3's rule is done, with the review it came from, and keeps its box line beside its shortcut line. The review also lists each lane carried across a changed patch as a shortcut line in step 3's form. Then comes one line for each issue the verifier found, inside the plan's boxes or outside them: `issue <n> <high|medium|low>: <what is wrong>. <command or repro>. <what it showed>. <what the intent requires>`. The severity is the verifier's view, and it may be strict. "No issues found" describes the search, not readiness to merge. Only a review from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not reviews, because neither runs the change as a user would.

   You decide whether the PR is accepted. For an issue that could cost a round, check the code and the evidence yourself, and rerun the repro where that settles it. Before you let a high issue stand, check it against the plan and ask what the reviews missed. Hold Autopilot-full step 4's bar, `playbooks/autopilot-full.md`. Calibrate your own judgment, not the verifier's, so never write a bar into a verifier's brief. You may argue an issue with the verifier in its session. Then fix it, let it stand, or defer it. Record your call as one comment at the head you accept:

   ```
   pstack-accept: head=<head sha> review=<url of the review comment> by=<your model>
   checked: <what you ran or read yourself>
   issue <n>: fixed in <sha> | stands. <why it does not block> | deferred to <owner>. <why it can wait>
   box <id>: changed. <earlier bar> to <new bar>, <who changed it>, <why>
   ```

   `checked:` names what you ran or read yourself. "Read the verifier's evidence at <path>" is an honest entry. Open each screenshot and video the PR carries, and name each in `checked:` with whether it shows the change. Each high and medium issue, and the issue of each failed box, gets an `issue` line with a written reason. A low issue needs no line. A deferral names its owner as `--defer` does in step 4, and why the issue can wait. A box whose bar changed after the plan was written gets a `box` line with the earlier bar, the new one, who changed it and why. A bar the operator reserved is theirs to change, not yours. Only the verifier writes a `pstack-review:` line, and only the lead writes a `pstack-accept:` line. A skipped box counts only when you accept it with a reason, or defer it to an owner, on the merge gate run that lands the PR (step 4). Accept a skip only for a box that does not apply, and defer a box whose work is owed, naming its owner, a Linear id. Until you accept or defer each skip, the gate refuses.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without your acceptance of a review that covers its head. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh review and your acceptance first, because its old review ran with that code beneath it and trunk does not have it.
3. **Re-check that the reviews still describe the code.** A review covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. So every review records the head it verified and that head's merge base with the PR's base branch, both taken when verification runs. Before trusting an older review, compare the whole-PR change it saw with the current one. Run `~/.agents/skills/poteto-mode/scripts/verdict-hash.sh <saved-merge-base> <review-head>` and `~/.agents/skills/poteto-mode/scripts/verdict-hash.sh <current-merge-base> <current-head>`. The review carries only when both succeed and print the same hash. A failure means it does not carry. Never hash `git diff` or `git patch-id` output by hand, because each can match code that runs differently, and the script is where those cases are tested. Use the saved merge base, never one recomputed from today's base branch, because a rebase moves it. Matching IDs carry the review to the current head. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both heads apart from noise. Noise is a difference that also shows up between two builds of the review head, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old review never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it unless it carries as a shortcut below, and re-verify anything else that drifted. The verifier may shorten re-verification after a rebase or a small change, but never skips it. The verifier reruns the merge brief's checks at the new head and reviews what changed since the earlier review, in the PR's own change (`git range-diff`) and in trunk under it. It may carry an earlier passing lane instead of rerunning it, even one with no build output, when nothing that changed reaches what the lane runs. The re-verification section of the project's verify skill, when it has one, says which changes reach which lanes. A change to code, config or a dependency the lane runs, or to the verify skill's steps for that lane, forces a rerun. The review lists each shortcut under its `pstack-review:` line as `shortcut <id>: <what was not rerun, and the review it carries>. <why nothing that changed reaches it>`. `<id>` is the box id when it shortens a box, such as `live-1`, and otherwise a lowercase slug with hyphens. The lead accepts each one on the gate run that lands the PR (step 4), or has it rerun. When code changes after a review, the new head needs a review. Send it to the verifier that wrote the earlier review, in its own session, with `t3_thread_send` to its thread. Tell it what was done and what you had the implementer fix, and ask it to re-verify. It answers in step 1's review format, and you decide again what to do and whether to continue. When a different model family wrote the fix, step 1's counterpart rule picks the verifier. When no code changed, your call needs no new review, so post your acceptance at the same head. Your acceptance carries with the review it names, so a rebase that step 3's hash carries needs no new acceptance.
4. **Land bottom-up, one PR at a time, only through the merge gate.** Always merge the run's lowest unmerged PR with `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo <owner/name> --pr <pr>`, adding `--plan <plan file> --plan-pr <PR id>` when the PR has a plan. `--repo` works from any directory, with or without a checkout of the repo. The gate prints the repo's merge brief first, so read it. A PR whose body declares its plan (`pstack-plan: <plan file> pr=<PR id>`, per `playbooks/opening-a-pr.md`) is checked against that plan without the flags, and the gate refuses when the plan it names is missing or differs from the one passed. With no plan either way, it says no plan was checked. Never run `gh pr merge` or arm auto-merge yourself. At the PR's current head, the gate checks that every check passed (Bugbot is not waited on), no review thread is open, the review covers the exact code (step 3's hash), the review lists every required box from the plan, your acceptance names that review and gives a line for each high and medium issue and each failed box, you accepted or deferred each skipped box and accepted each shortcut, Codex has reviewed that head, and Lee approved the exact text of any AGENTS.md or CLAUDE.md change. Lee approves in chat, in the T3 thread where an agent showed the exact text. That agent then posts one PR comment with the gate's `lee-approves-instruction-files: <hash>` line, an `approved-in: <T3 thread id>` line and Lee's words quoted, and never posts it without that approval. The hash ties the approval to that text, so any later edit needs Lee's yes again. A PR that syncs from an upstream repository declares the upstream commit it syncs to on its own line in the body, `pstack-upstream: <owner/repo>@<sha>`. An AGENTS.md or CLAUDE.md file needs no approval when it is byte-identical at the head to upstream's at that commit, or both have removed it, and the fork had not changed it from upstream before the sync, because the fork did not write it. The gate checks that the commit is on upstream's default branch and in the PR's history, and every file the fork wrote or edited still needs Lee's approval. If anything is missing it merges nothing and prints what is missing and what to do. Otherwise it merges, reads the PR back, and fails unless it reads merged into trunk. To accept a skipped box, add `--accept-skip <id>=<reason>` once per box. To defer one whose work is owed, add `--defer <id>=<owner>`, where the owner is a Linear id. To accept a shortcut the review lists, add `--accept-shortcut <id>=<reason>`. To merge past a missing CI check, an open review thread, or a missing Codex review, add `--waive <checks|threads|codex>=<reason>`. The review on the exact code, your acceptance and the instruction-file approval cannot be waived. The gate posts the waivers, deferrals and accepted shortcuts on the PR before it merges and records them in its run log. `--check` runs the same checks without merging. `merge-gate audit [--repo <owner/name>] [--since <YYYY-MM-DD>]` lists merges that have no gate receipt and saves the table under `merge-gate/audit/` in the pstack store. It also lists each skip, deferral, shortcut and waiver the lead accepted on a gated merge, with its reason or owner. It lists a gap that `--known <owner/name>#<pr>@<head>` names apart from new ones, and one that `--historical <owner/name>#<pr>@<head>=<reason>` settles as historical, never as receipted. In each repo it audits, the window reaches back to the oldest gap that the latest earlier audit file listing it left unresolved, until `--historical` settles that gap. `--unreachable <host>` names a host whose receipts it could not read. It exits 0 when every merge is receipted or historical, 1 on any new or known gap, and 2 on a usage or read error. Run it at each job's close-out. It also runs daily, and the retro round reads its results. The gate squash-merges by default. Pass `--method merge` when the repository requires merge commits, as `liminal-ai/t3code-v2`'s `FORK.md` does. The gate works through `gh`, so on Origin stop and report. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The review covers the patch, not its commits, so step 3's diff rule decides whether the review survives. Run the gate on it once its checks pass.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, reviewed or not. On both forges, keep the fallback heartbeat per the Waking and polling section of the role file (`~/lim-v2/AGENTS.md` or `~/lim-v2/CLAUDE.md`), because a watch ends on merge and the heartbeat is what notices it. On GitHub, arm `watch_pull_request` on the run's current bottom PR. On each wake, run the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top> --status-only`), read the PR back as step 4 says, and re-arm the watch on the new bottom PR, until the ceiling reads merged. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new reviews and acceptances, so it is a new pass through step 1.

**Reply:** catch the operator up per the **ketchup** skill, covering the verified run and its ceiling, each PR's review and who wrote it, your acceptance of each (what you checked, what you let stand or deferred, and why), what landed and how you confirmed it, and what the next gap needs.
